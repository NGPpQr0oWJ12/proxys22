# Терминальная утилита proxys22

Публичный репозиторий: [NGPpQr0oWJ12/proxys22](https://github.com/NGPpQr0oWJ12/proxys22).
Готовые программы и актуальные образы: [GitHub Releases](https://github.com/NGPpQr0oWJ12/proxys22/releases/latest).
Поддерживается **только Keenetic Start KN-1112**.
Перед обновлением модель и платформа определяются по SSH до скачивания образа.
Другие модели можно опознать на работающем OpenWrt, но запись для них блокируется.

## Запуск

Windows x64: скачайте `proxys22-<версия>-windows-x86_64.exe` и запустите его.
Linux x64: скачайте `proxys22-<версия>-linux-x86_64`, разрешите исполнение
`chmod +x proxys22-<версия>-linux-x86_64` и запустите файл в терминале.
Сборка GitHub для Linux рассчитана на glibc 2.35 и новее; для других систем
можно запустить исходный код с Python 3.10+.
В готовые программы Python, библиотека SSH и TFTP-сервер уже включены.

Без аргументов открывается оформленное русское меню. Подсказки, ошибки и подтверждения
также выводятся на русском. Цвет включается в поддерживаемом терминале; `NO_COLOR`
отключает его. При перенаправлении вывода в файл остаётся обычный текст без ANSI-кодов.
В командах ниже `proxys22` означает путь к скачанной программе.

```text
proxys22 releases
proxys22 download --kind factory --output ./firmware
proxys22 download --kind sysupgrade --output ./firmware
proxys22 flash --bind 192.168.1.2
proxys22 detect --host 192.168.2.1
proxys22 detect --host 192.168.2.1 --json
proxys22 diagnose --host 192.168.2.1
proxys22 backup --host 192.168.2.1
proxys22 update --host 192.168.2.1
proxys22 doctor --online
```

Запуск из исходников:

```text
python -m pip install -r requirements-manager.txt
python proxys22.py
```

Глобальные параметры ставятся **перед** командой:

```text
proxys22 --tag v0.4.1 download --kind factory
proxys22 --manifest ./firmware/proxys22-release.json flash --bind 192.168.1.2
proxys22 --manifest ./firmware/proxys22-release.json update --host 192.168.2.1
```

Последние две команды работают без доступа к GitHub, если рядом с JSON-манифестом
лежат оба оригинальных образа этого релиза. Локальный файл можно явно выбрать через
`--image`; его SHA-256 и размер всё равно сверяются с манифестом.
Сам манифест и образы следует получать из одного доверенного релиза.

## Первичная прошивка

`flash` загружает **factory**, проверяет модель назначения, размер и SHA-256, затем
показывает проводную процедуру восстановления. После подтверждения `ПРОШИТЬ KN-1112`
он запускает существующий TFTP-сервер, выдающий только `KN-1112_recovery.bin`.

Если на устройстве ещё работает OpenWrt с доступом по SSH, добавьте
`--host <адрес>` к `flash`: модель будет проверена перед скачиванием и запуском TFTP.
В меню для этого есть отдельный запрос адреса; Enter означает работу только с загрузчиком.
Ошибка SSH или неизвестная модель при указанном адресе останавливает процедуру без автоматического обхода проверки.

Закрытая штатная прошивка или сам загрузчик могут не предоставлять достоверную модель
и аппаратную ревизию. В этом случае автоматического определения по MAC, IP или названию Wi-Fi нет:
нужно сверить полную модель на наклейке и подтвердить `ПРОШИТЬ KN-1112`.
Правильное имя TFTP-запроса подтверждает только запрошенный профиль образа;
оно не доказывает аппаратную ревизию. Любое другое имя отклоняется без передачи прошивки.

До запуска сохраните штатные настройки и образ возврата KeeneticOS, подключите LAN 1–3,
отключите WAN и подготовьте выбранный проводной адаптер: `192.168.1.2/30`.
На Linux для UDP 69 могут понадобиться повышенные права; на Windows разрешите процессу
необходимый входящий UDP на выбранном интерфейсе. Утилита не меняет адреса,
маршруты или межсетевой экран автоматически.

Запись запускает загрузчик, когда владелец вводит устройство в режим восстановления:
при выключенном питании удерживать Reset, включить питание, отпустить Reset при мигании Power.
Не отключайте питание до окончания записи и перезагрузки. Передача TFTP сама по себе
не подтверждает успешную загрузку ОС.
Полная процедура и возврат сетевых настроек: [recovery.md](recovery.md).

Резервную копию **штатной KeeneticOS** можно отдельно получить существующим
`scripts/backup-keenetic.py`; команда `backup` новой утилиты предназначена для установленной proxys22.

## Обновление

`update` получает последний опубликованный стабильный релиз из GitHub, а не предварительную
сборку. `--tag` позволяет выбрать конкретный стабильный релиз. Перед записью утилита:

1. Подключается по SSH, определяет модель и проверяет `keenetic,kn-1112`, платформу OpenWrt и маркер proxys22. Неподдерживаемая модель останавливает операцию до загрузки образа.
2. Получает подходящий релиз для KN-1112, проверяет манифест, платформу, тип **sysupgrade**, размер и локальный SHA-256.
3. Сохраняет локальную копию `sysupgrade -b`, проверяет читаемость архива и наличие
   существующих сетевых настроек, маркера и профилей AmneziaWG/Hysteria.
4. Передаёт образ, сверяет SHA-256 на роутере и выполняет `sysupgrade -T`.
5. Запрашивает слово `ОБНОВИТЬ` и только после него запускает штатное обновление с сохранением настроек.

Скачивание, отправка по SSH и передача загрузчику показывают процент по фактически
переданным байтам. Обновление разделено на семь этапов с отдельным результатом проверки
SHA-256. **100% передачи не означает окончание записи прошивки или успешную загрузку ОС.**
Утилита не вычисляет вымышленный процент записи во флеш-память.

Ключи `-F` и `-n` не используются. Повреждённые образы, другая модель, неполная копия
или ошибка проверки останавливают процедуру. Понижение версии запрещено.
Для переустановки той же версии нужен явный `--reinstall`.

После принятия команды начинается перезагрузка; это ещё не подтверждение успешной загрузки.
Дождитесь устройства и выполните `diagnose`, проверьте версию, сеть и туннель.
Резервный образ предыдущего релиза сохраните до обновления; возврат выполняется по процедуре восстановления.

## Определение модели без прошивки

Пункт **8** в меню или `detect --host <адрес>` читает только `ubus call system board`
по SSH и показывает модель, идентификатор платы, платформу, ЦП и наличие совместимой сборки.
Наличие установленной proxys22 не требуется. `--json` выводит выбранные поля для автоматизации;
профили VPN, ключи и полные системные ответы в отчёт не включаются.
Распознавание неизвестного устройства не означает поддержку прошивки: поле `supported` будет `false`.

Если модель не отвечает через OpenWrt ubus, утилита сообщает, что определить её не удалось.
Она не подставляет KN-1112 по умолчанию. О поддержке Cudy WR1200E 2.0 — [сравнение оборудования](hardware.md).

## SSH, резервные копии и диагностика

Пароль запрашивается скрыто и не записывается на диск. Для ключа используйте
`--identity /path/to/key`; доступен и штатный SSH-agent.
При первом подключении нужно проверить отпечаток SSH-ключа и подтвердить `ДОВЕРЯЮ`.
Это сохраняет ключ устройства; запуск обновления подтверждается отдельно словом `ОБНОВИТЬ`.
Регистр букв не важен. Enter отменяет подтверждение.
Изменившийся известный ключ блокирует подключение.

Каталог состояния по умолчанию — `%LOCALAPPDATA%/proxys22` на Windows и
`$XDG_STATE_HOME/proxys22` или `~/.local/state/proxys22` на Linux.
В нём находятся `known_hosts`, кэш проверенных прошивок и закрытые резервные копии.
Архивы содержат настройки и секреты VPN; храните их приватно, не добавляйте в Git и не публикуйте.
`--state-dir`, `--cache-dir`, `backup --output` и `update --backup-dir` позволяют выбрать другие каталоги.

`diagnose` только читает состояние: модель, версию, память, источник Интернета,
активный протокол, маршрут и состояние туннеля. Сырые конфиги, ключи, пароли,
список клиентов и содержимое журналов в отчёт не включаются. По умолчанию это оформленный
русский отчёт; `diagnose --json` выводит исходные машинные поля JSON для автоматизации.
`doctor` проверяет локальную среду; `--online` дополнительно проверяет доступ к стабильному релизу.

## Сборка и выпуск

```text
python -m pip install -r requirements-manager-build.txt
python scripts/package-manager.py
```

Сборка выполняется отдельно на Windows и Linux. Новый релиз использует одну версию
в `config/build.json`, `overlay/etc/proxys22-release` и `proxys22_manager/__init__.py`.
`scripts/build-firmware.sh` создаёт образы, `proxys22-release.json` и `sha256sums`.
Workflow `.github/workflows/release.yml` проверяет код на обеих ОС и по тегу `vX.Y.Z`
собирает программы и прошивку, затем публикует их вместе в GitHub Releases.
Ручной запуск workflow только собирает артефакты, без публикации.

Программные тесты не прошивают устройство. Первичную запись, загрузку новой ОС,
радио и реальную работу туннеля нужно отдельно проверять на физическом KN-1112.
